# Приближённая солёность и профиль вычислений

Изменение поверх `af72d97652021f02e69a665fcd50b9d63815f792`, 5 ноября 2026.
Баланс соли расширяет отдельный глобальный гидросценарий. Он не меняет
выемку, перенос грунта, энергетику, наземные маршруты или часы техники.
Водная эрозия отложена на следующий этап.

## Соль

Впадина считается одним перемешанным резервуаром. Состояние содержит полную
массу соли `M`, включая растворённую часть и сухой осадок. Для каждого
прежнего водного шага:

```
M_ввоз = C_притока * V_притока
M_растворено = min(M, C_предел * V_воды)
C = M_растворено / V_воды
M_осадок = M - M_растворено
M_вывоз = C_перед_переливом * V_перелива
M - M_начальное - ΣM_ввоз + ΣM_вывоз = погрешность баланса
```

Единицы: объём м³, соль кг, концентрация **г/л = кг/м³**. Это не PSU и
не массовая доля г/кг или ‰: пересчёт к ним потребовал бы плотности раствора.
Испарение не уносит соль. При высыхании концентрация не определена, а соль
остаётся осадком. При новом наполнении осадок сразу растворяется до предела.
Перелив после изменения вместимости уносит только растворённую часть хорошо
перемешанного раствора; осадок не смывается. Мутный поток не моделируется.

Значения по умолчанию: **38 г/л** для морского притока, **300 г/л** для
условного предела растворимости. Первое — приближённое исходное допущение
для средиземноморского сценария, не измерение воды на выбранном берегу.
Второе — эффективный модельный предел смеси солей, не точная химическая
характеристика морской воды. Доступно изменение обоих значений.

Новая сухая впадина не содержит исходного солевого запаса. Растворение солей
в грунте, грунтовые воды, температурная растворимость, отдельные ионы,
стратификация, плотностные течения и замедление испарения рассолом отсутствуют.
Поэтому расчёт показывает сценарную оценку, а не гидрохимический прогноз
реальной Каттары. Испарение и пропускная способность канала остаются прежними.

Даже если водный уровень не меняется при `Q_притока = Q_испарения > 0`, соль
продолжает накапливаться. Аналитический пропуск неподвижного водного состояния
теперь учитывает этот приток соли без дополнительных численных решений.
При почти сухой впадине не вводятся микроскопические шаги из-за концентрации.

## Управление и сохранения

**Ландшафт / импорт DEM… → Водоём / прокоп… → Соль…**. Солёность и массы
показаны под картой; отдельная вкладка строит историю концентрации. Сухие
интервалы и неизвестный старый состав оставляют разрыв графика. Настройка
будущего притока сохраняет прежнюю соль и весь водный баланс. Галочка
**Задать состав имеющейся воды заново** явно заменяет текущую исходную оценку,
включая прежний осадок, и начинает новый солевой баланс с текущего времени.
При открытом окне настроек расчёт воды приостановлен.

```
python -m ats --headless --qattara \
  --channel-route docs/ats2/qattara-channel.json --steps 0 \
  --instant-channel --flood-days 365 --salt-inflow-g-l 38 \
  --solubility-g-l 300 --flood-report salt.json --save-state salt.atsstate

python -m ats --headless --load-state salt.atsstate --steps 0 \
  --flood-days 365 --save-state salt-2years.atsstate --flood-report salt-2years.json
```

`--initial-salinity-g-l` — явная замена текущей исходной оценки, а не
поправка к прошлому притоку; для обычного продолжения этот флаг не нужен.
В JSON доступны концентрация, происхождение оценки, растворённая/осаждённая
масса, ввоз, вывоз, исходная масса и ошибка баланса соли.

Новые `.atsstate`: версия **16**, читаются **1–15**. Новые `.atsregion` с
водой: версия **5**, читаются **1–4**. Водный объект: версия **2**, читается
прежняя **1**. Формат региона без воды не повышается. Старые исходные файлы
не изменяются; продолжение пишется обычной командой в выбранный новый файл.

При миграции прежнего водного сценария:

- Сухой старт без перелива позволяет оценить накопленную соль как
  `38 * записанный суммарный приток`. UI явно помечает **оценка из прежнего
  притока**. Старые строки истории не получают выдуманных значений солёности.
- При исходном запасе воды или переливе состав восстановить однозначно нельзя.
  Вода продолжает считаться, солёность помечена неизвестной. Пользователь
  задаёт исходную концентрацию через **Соль…**, если нужен солевой расчёт.
- Уже накопленный грунт, оборудование, грузы, энергия и часы сохраняются.

## Что сейчас занимает время при копании

Короткий `cProfile` на Linux/Python 3.12, физический шаг 1 с, исходный код
земляных работ `af72d97`. Два разных сценария, по 120 модельных секунд:

1. Штатная прибрежная Каттара: NOAA DEM, окно 512 м / 1024² ячейки,
   4 дрона, 45 платформ сезонного комплекта, 4866 м² PV. Предварительно
   выполнены 480 с; Крот копает все 120 с, переездов за интервал нет.
2. `benchmark_world_terrain.py --runtime-fixtures`: 14 комплексов × 4 дрона,
   общая карта 512 м / 512², по 68 м² PV, условные слои. После 45 с расстановки
   измерены следующие 120 с. На старте 13 Кротов в локальном движении,
   один ждёт; это не 14 больших сезонных баз в стационарной работе.

| Функция / подсистема | Каттара, 1 комплекс | 14 комплексов |
|---|---:|---:|
| `Planner.choose`, вместе с вложенными проверками | 6,36% / 4 вызова | 5,70% / 49 вызовов |
| `Terrain.dump_location`, входит в планирование | 3,63% / 129 вызовов | 1,62% / 49 вызовов |
| `Terrain.relax`, осыпание | 1,43% / 3 вызова | 1,05% / 183 вызова |
| `Logistics.sync_batteries`, вместе с вложенными проверками | 20,60% | см. полный профиль |
| `SharedSite._refresh_geometry`, вместе с подготовкой ключей | — | 48,89% / 63257 вызовов |
| `regional.ground_route`, наземный маршрут при переходе | 0 вызовов | 0 вызовов |

Это **включающие** времена функций, вложенные строки нельзя складывать.
Например, 35,55% на `_geometry_key` уже входят в 48,89% `_refresh_geometry`.
Геометрия не строилась заново 63257 раз: это вызовы проверки актуальности;
каждый такой вызов проверяет ключи 14 участников. Получилось 885598 вызовов
`_geometry_key`, около 7380 на модельную секунду. Полётные проверки вызывают
их многократно, хотя данные в пределах одного шага часто неизменны.

Для одиночной базы заметны синхронизация установленного оборудования,
позиции/состояния батарей, валидация инвентаря, маска досягаемости Крота,
пылевая модель и проверка полётных препятствий. Выбор отвала не является
основной затратой всего текущего прогона. Но в одиночном планировщике
32 кандидата забора всё ещё могут вызывать 32 поисковых проверки отвала.
В общей карте ближайшая площадка уже переиспользуется при сравнении
кандидатов, что видно по 49 вызовам на 49 назначений.

На том же одиночном снимке с offscreen Qt подготовка пяти кадров заняла
0,272 с, отрисовка четырёх — 0,063 с. Измеренный интервал Qt-таймера максимум
172 мс. Физический отчёт с UI совпал с headless побитово по хэшу JSON.
Это профилированные короткие проверки, а не пользовательский FPS или
воспроизведение его длительных зависаний после 23 модельных часов.

Дорогой наземный A* при переносе всей группы — отдельная синхронная операция
подготовки переезда; его прежние 24 с нельзя относить к каждому рейсу дрона.
Постоянная точка копания не уберёт необходимость проверить этот путь.

## Можно ли копать и сбрасывать в фиксированные точки

Для одного участка можно переиспользовать несколько опорных точек, пока
они пригодны. Это разумное упрощение планировщика, но не замена проверок:

- Ковш снимает грунт в своём небольшом пятне. После достижения проектного
  дна соседние устойчивые уступы не обязаны осыпаться. Особенно при широком
  плоском дне или прочном нижнем слое один колодец не образует весь канал.
  Нужна сетка/ряды точек и проверка остаточного проектного профиля.
- Фиксированная точка отвала образует конус с конечной высотой и пятном.
  Осыпание перемещает только неустойчивый грунт; оно не переносит насыпь
  по ровной поверхности к далёкому свободному месту. После заполнения точки
  нужно смещать выгрузку, сохраняя границы, вместимость и проходы.
- Несколько дронов не могут безопасно одновременно занять одну точку.
  Резервы забора/выгрузки, грузоподъёмность, энергозапас и коллизии нужны.

Приоритет дальнейшей оптимизации по этим замерам — повторные проверки ключей
общей геометрии, затем неизменный состав оборудования/позиции батарей.
После этого имеет смысл переиспользовать площадку отвала для нескольких
кандидатов одиночного планировщика с инвалидизацией по заполнению,
изменению грунта и резервов. В данном изменении планировщик не заменялся.

## Воспроизведение

Завершённые локальные проверки: **727 тестов**, включая **20 новых солевых**,
и **10 прежних групп CLI / 32 команды**. Проверены приток, концентрация при
испарении, сухой остаток и повторное растворение, насыщение, вынос при
уменьшении чаши, аналитическое равновесие воды с накоплением соли, ручная
исходная оценка, старые `.atsstate` v15 / `.atsregion` v4, продолжение и Qt.
Полный набор также покрывает прежние переезды, баланс грунта и энергетику.
Windows/CI для этого локального изменения ещё не запускались.

Для канала 20×5 м длиной 84,73 км, среднего испарения 5 мм/сутки и сезонной
доли 0,5, при сухом старте и притоке 38 г/л:

| После | Объём воды | Средняя растворённая соль | Невязка соли |
|---|---:|---:|---:|
| 1 года | 2,3797 км³ | 42,4225 г/л | 0 кг |
| 10 лет | 12,7772 км³ | 79,0101 г/л | 0 кг |

Это результат конкретного условного сценария без исходных солей дна.
Десять лет рассчитаны за 14600 водных шагов; медиана времени одного года
0,826 с. Уменьшение максимального шага с 6 до 1,5 часа изменило концентрацию
первого года на 0,00219 г/л, не являясь проверкой климатической достоверности.

Парное сравнение с опубликованным `af72d97`: три повтора по два года,
чередование порядка старого/нового расчёта. Медианы **1,857 с → 1,903 с**;
все проверенные водные величины и число шагов совпали точно. Разница около
2,4% меньше межпрогонного разброса (старый 1,718–2,007 с, новый
1,784–1,958 с), поэтому точный процент накладных расходов этим коротким
контролем не установлен. Соль не требует ещё одного решения водного баланса.

```
python -m pytest -q
python -m pytest tests/test_salinity.py tests/test_hydrology.py -q
python scripts/benchmark_flooding.py --years 10 --output salt-benchmark.json

python -m ats --headless --qattara \
  --channel-route docs/ats2/qattara-channel.json --energy-preset qattara-season \
  --steps 480 --save-state coast.atsstate --json coast.json
python scripts/benchmark_runtime.py --state coast.atsstate --steps 120 \
  --trials 1 --profile coast-profile --output coast-profile.json
python scripts/benchmark_runtime.py --state coast.atsstate --steps 120 \
  --mode gui --offscreen --trials 1 --profile coast-ui-profile --output coast-ui.json

```

Скорости под профилировщиком зависят от его накладных расходов. Сравнивать
их напрямую со скоростью на домашнем ПК нельзя. Параметры и полные таблицы
профиля сохранены в `salinity-runtime-validation.json`.
