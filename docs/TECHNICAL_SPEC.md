# Техническое задание: Autonomous Terraforming Simulator (ATS)

## 0. Задача для Codex

Создай **работающее настольное приложение на Python**, а не концепт, мокап или набор заглушек. Это инженерная песочница: один автономный тяжёлый электрический мультикоптер с подвесным грейфером выкапывает заданную канаву, переносит песок в отвал, возвращается на солнечную гусеничную базу для зарядки. Рельеф изменяется физически согласованно; песок осыпается; энергия конечна; под винтами возникает визуализируемая пыль.

**Приоритет — завершённый, проверяемый MVP**, а не реалистичность любой ценой. Сначала реализуй все обязательные функции ниже; воду, эрозию, фотореалистичную графику, CFD и несколько дронов не добавляй. Используй разумные допущения и документируй их. Не останавливайся после плана: создай файлы проекта, установочные инструкции и тесты, запусти доступные проверки и исправь найденные ошибки. Если окружение не поддерживает GUI, отдельно проверь headless-движок.

## 1. Технологии и архитектура

- Python 3.11+; `numpy`, `PySide6`, `pyqtgraph`, `pytest`. Дополнительные зависимости — только при обоснованной необходимости.
- Проект должен запускаться на Windows и Ubuntu (без привязки к системному окружению).
- **Чистый вычислительный движок отдельно от GUI**: `Simulation.step(dt)` работает без Qt и без окна.
- Единицы строго SI: метры, килограммы, секунды, ватты, джоули. В интерфейсе энергию отображать в кВт·ч.
- Внутри симуляции фиксированный шаг `dt = 1 с` (либо другой фиксированный шаг, если тесты демонстрируют его пригодность), отображение обновлять независимо. Временное ускорение — 1×, 10×, 50×, 200×. Не умножать просто физический шаг на 200.
- Расчёты должны быть детерминированными при одинаковом `seed`, настройках и последовательности шагов.
- UI не должен замерзать во время моделирования: QTimer с ограниченным бюджетом вычислений на кадр либо отдельный worker с безопасной передачей снимков состояния.
- Хранить все настраиваемые константы в одном месте (`config.py` или dataclass-конфигурация); не разбрасывать «магические числа» по коду.

## 2. Карта и грунт

- Мир — **2.5D heightfield**: регулярная сетка высот `height[y, x]` формата NumPy (`float64` для расчётов). Начальный размер 128×128 ячеек, шаг 0,25 м, участок 32×32 м.
- Начальная поверхность почти плоская, допустимы небольшие воспроизводимые неровности; предусмотреть режим полностью плоского рельефа.
- На старте только **один материал** — сухой рыхлый песок с постоянной насыпной плотностью 1600 кг/м³. Не смешивать массу и объём: изменение высоты одной ячейки на Δh меняет объём на `ΔV = Δh * cell_size²`, массу — на `Δm = density * ΔV`.
- Пользователь задаёт канаву: длина, **ширина плоского дна**, глубина, положение и ориентация (для MVP достаточно вдоль оси X). Пресет «Демо» по умолчанию: длина 2 м, дно 1 м, глубина 0,25 м. Дополнительно пресеты «Средний» (5×1,5×0,5 м) и «Большой» (10×2×1 м). Значения — длина × ширина дна × глубина.
- Канава должна быть физически реализуемой для сухого песка: целевая поверхность состоит из плоского дна и откосов под заданным углом естественного откоса (по умолчанию 35°). **Ширина дна — не верхняя ширина выемки**. Для каждой точки вне прямоугольника дна использовать расстояние до его границы: `target_height = min(initial_reference_height, bottom_height + tan(angle) * distance_to_bottom_rectangle)`. Внутри дна — `bottom_height`. На концах также нужны откосы. Начальный ровный уровень можно считать равным нулю.
- Участок отвала — заданная прямоугольная область, удалённая от канавы. Весь выкопанный песок должен быть складирован на карте, не исчезать.
- Захват грунта: грейфер извлекает до своей текущей грузоподъёмности песок из небольшой области (радиус порядка 0,5 м). **Не извлекать больше объёма, чем реально имеется сверх целевого профиля**. Распределять выемку по нескольким ячейкам, а не делать глубокую дыру одной ячейкой.
- Выгрузка: добавлять такой же объём в соседние ячейки зоны отвала, с формированием насыпи. Нельзя «телепортировать» грунт без учёта груза и событий погрузки/разгрузки.
- Осыпание: простой консервативный алгоритм обмена грунтом между соседними ячейками при превышении допустимого уклона. Соседние пары должны переносить **объём без создания или уничтожения массы**; контролировать устойчивость алгоритма. Сложные дискретно-элементные расчёты не нужны.
- Края карты закрыты: грунт не должен пропадать за границами. Отображать предупреждение, если отвалу не хватает места.

## 3. Электрический строительный дрон

Один дрон, условно похожий по классу на тяжёлый грузовой мультикоптер с лебёдкой. Это **не точная цифровая копия** какой-либо конкретной модели.

Параметры по умолчанию (легко меняются через конфигурацию):

| Параметр | Стартовое значение |
|---|---:|
| Масса пустого аппарата с оборудованием | 105 кг |
| Максимум песка в грейфере | 60 кг |
| Батарея дрона | 5 кВт·ч |
| Обязательный резерв энергии | 20% |
| Горизонтальная скорость без груза | 6 м/с |
| Горизонтальная скорость с грузом | 4 м/с |
| Рабочая высота над местным рельефом | 6 м |
| Время захвата/выгрузки грунта | по 10 с |
| Потребление в висении без груза | 18 кВт (модельная оценка) |

- Координаты `(x, y, z)`, текущая скорость, уровень заряда, масса груза, состояние автомата.
- Движение непрерывное, с конечной скоростью, без мгновенных прыжков. Для MVP не нужна полная динамика шести степеней свободы, аэродинамические моменты и управление отдельными моторами.
- Безопасный полёт над рельефом: выдерживать высоту над поверхностью, проверять прямую траекторию на столкновения с землёй и базой. Не допускать попадания позиции дрона под поверхность.
- Погрузка — **подвесной грейфер на тросе**. Мультикоптер зависает над местом выемки, грейфер опускается и захватывает рыхлый песок. Механическое взаимодействие грейфера и грунта можно упростить до дискретного события; учесть время операции и энергозатраты.
- Потребляемая мощность приближённо зависит от взлётной массы, например `P_hover = P_empty * (M_total/M_empty)^1.5`, с ограничениями и дополнительной небольшой поправкой на горизонтальный полёт. Константы приблизительные, не представлять их как подтверждённые результаты испытаний.
- Перед вылетом дрон оценивает расход энергии на дорогу, работу и **обязательное возвращение** с резервом. Если энергии недостаточно, остаётся на зарядке. Если солнца нет и база разряжена, ждёт; батареи не становятся отрицательными.
- Конечный автомат: `DOCKED/CHARGING → TAKEOFF → TO_DIG → LOWER_GRABBER → SCOOP → LIFT_GRABBER → TO_DUMP → DUMP → RETURN → LANDING → DOCKED`. Прописывать безопасное поведение при невозможности выкопать грунт, недостаточной энергии и заполненном отвале; не допускать бесконечных мгновенных переходов.
- Планировщик выбирает участок с избытком высоты над `target_height`, учитывая расстояние, объём доступного песка, энергетический бюджет. Сначала простой жадный алгоритм; сложный AI/RL не нужен.

## 4. Мобильная солнечная база

- Отдельный объект, а не просто бесконечная зарядная станция. Имеет координаты, запас энергии, солнечные панели, скорость движения и состояние.
- Значения по умолчанию: площадь панелей 20 м²; КПД 20%; батарея базы 30 кВт·ч; максимальная мощность зарядки дрона 8 кВт; эффективность зарядки 90%; скорость гусениц 0,2 м/с; потребление при движении 1 кВт. Все параметры настраиваемые.
- Суточная генерация: упрощённая периодическая кривая солнечного излучения с нулём ночью и максимумом порядка 1000 Вт/м² в полдень. Учесть время суток. Генерация не может превышать `irradiance × area × efficiency`, энергия не возникает сама собой.
- Зарядка дрона **только на базе, после посадки**, со списанием энергии из аккумулятора базы и учётом потерь. Нельзя одновременно приписывать одну и ту же солнечную энергию обоим аккумуляторам.
- База должна уметь **реально перемещаться по поверхности на гусеницах**, медленно и редко, без телепортации. Пока движется, панели сложены и генерация приостановлена. Для MVP допустимо движение только по подходящему относительно ровному маршруту, с проверкой высоты/уклона и запретом пересечения канавы.
- Автоматическое перемещение по простому критерию: после нескольких рейсов, при существенном выигрыше в длине маршрута и при пристыкованном дроне; применять ограничение частоты перемещений. Если безопасный путь не найден — оставаться на месте и продолжать доступную работу.
- Показывать состояние базы: `PARKED_GENERATING`, `CHARGING`, `MOVING`, `WAITING_FOR_SUN`. Допустима генерация и зарядка одновременно, если правильно ведётся баланс мощности.

## 5. Пыль — дешёвая визуальная модель, не CFD

- При низком зависании и работе грейфера в сухом песке появляется пыль от воздушного потока винтов. Интенсивность эмиссии зависит качественно от массы/мощности дрона, высоты над грунтом, сухости песка и стадии работ.
- Пыль представлять **скалярным полем концентрации** на сетке (желательно пониженного разрешения) либо компактными визуальными облаками. Добавить перенос ветром, рассеивание и затухание. В интерфейсе рисовать полупрозрачное облако, следующее за ветром, а не просто круг, намертво прикреплённый к дрону.
- Это качественная модель видимости, **не реальное вычисление аэродинамики**. В версии 1 пыль не вычитает массу из рельефа, чтобы не нарушать баланс. Не симулировать миллионы песчинок, полноценную турбулентность или Navier–Stokes.
- Пользователь может регулировать ветер, силу визуального пылеобразования и включать/отключать отображение пыли.

## 6. UI и графика

Основной ориентир — понятный инженерный симулятор, а не игровая картинка.

**Обязательно:**

1. Главное окно PySide6. Большая интерактивная карта сверху через `pyqtgraph`/Qt: цветовая карта высот с рельефной подсветкой (hillshade либо контуры), отдельно выделенные дно и откосы проектной канавы, отвал, дрон и база. Позиции объектов обновляются в реальном времени.
2. Показывать саму форму изменяющегося рельефа: цвет по высоте, при необходимости контурные линии. Участок выемки и складирования можно выделить разными полупрозрачными масками; не закрывать ими рельеф полностью.
3. Визуализация пыли полупрозрачным слоем. Можно добавить тень дрона и индикатор массы груза.
4. График продольного или поперечного профиля канавы: **текущая линия высоты против проектной**, чтобы ясно было видно осыпание.
5. Панель: Play/Pause, Reset, скорость 1×/10×/50×/200×, параметры проекта канавы, угол откоса, ветер, мощность солнечных панелей; кнопка нового сценария.
6. Телеметрия: время симуляции и время суток; общий объём вынутого грунта; текущий объём оставшейся выемки; процент готовности; число рейсов; груз; заряд дрона и базы; текущая мощность солнечной генерации; расход энергии; статус дрона и базы.
7. Журнал событий: «завершена выемка», «ожидает зарядки», «началось осыпание», «база перемещается», «работа завершена»; не спамить одинаковыми событиями каждый шаг.

**Не требуется для MVP:** фотореалистичные модели винтов, камера от первого лица, физические частицы, сложная 3D-сцена. Если основной функционал стабилен, добавить **опциональный** 3D-вид heightfield (например, OpenGL) отдельным этапом, без ущерба FPS. Для первой версии хорошая 2D-карта и профиль важнее красивого, но медленного 3D.

## 7. Сценарий и завершение задачи

Стартовый сценарий **по умолчанию — быстрый «Демо»**: ровный участок 32×32 м, канава 2×1×0,25 м (1 м — ширина дна), откос 35°, зона отвала вне канавы, одна база и один дрон. Это нужно, чтобы увидеть завершённую миссию без многочасового ожидания в реальном времени. Пресет «Большой» 10×2×1 м доступен по выбору и рассчитан на длительное моделирование. Целевой объём выемки определяется **геометрией дна и откосов**, а не простым произведением длины, ширины и глубины.

После запуска алгоритм сам планирует рейсы, роет, складирует песок, при необходимости ждёт солнца/заряда, изредка перемещает базу и показывает изменение грунта. Пользователю не приходится поштучно командовать рейсами.

Условие завершения: остаточный объём грунта **над проектной поверхностью** внутри проектной выемки меньше допуска (например, 0,05 м³); дрон не несёт песок; не зацикливается попытками достать недоступную «долю ячейки». В конце вывести количество рейсов, часы/дни, суммарный расход энергии, полученную солнечную энергию, вынутую массу и погрешность баланса грунта.

Если выполнение невозможно (недостаток места в отвале, неправильная конфигурация, препятствие), система должна сообщать конкретную причину вместо бесконечного ожидания.

## 8. Численная корректность и тесты

- Контроль **сохранения массы песка**: `масса_грунта_на_карте + масса_груза_в_дроне` должна оставаться постоянной с учётом согласованного начального базового уровня. Осыпание — только перераспределение, выемка/выгрузка — только перенос.
- Консервативный перенос по сетке; тест с многократной выемкой/выгрузкой и осыпанием. Допуск к суммарной массе — численная погрешность float64, не проценты потерь за каждый рейс.
- Заряды обоих аккумуляторов всегда лежат в `[0, capacity]`; проверять энергетический баланс солнечной генерации, потребления и зарядных потерь.
- Проверять, что дрон не оказывается под поверхностью, а груз не превышает заданную грузоподъёмность.
- Один и тот же seed даёт одинаковые результаты в headless-режиме.
- Тест маленькой канавы (например, 2×1×0,25 м): симулятор должен прийти к состоянию `COMPLETED` за разумное виртуальное время; тест должен иметь верхний предел шагов и не зависать.
- Тест невозможного сценария: состояние `BLOCKED` с описанной причиной.
- Автоматические тесты через `pytest`; запуск симуляции без GUI из CLI, например `python -m ats --headless --steps 10000 --seed 42`. Подобрать точные команды и зафиксировать в README.
- Минимальная профилировка при 128×128: рельеф/GUI не должны перерассчитываться неоправданно часто. Не пытаться оптимизировать заранее всё; применять NumPy и локальные изменения, потом профиль.

## 10. Порядок реализации и границы этапов

**Этап A — работающий физический контур без UI:** сетка, целевая канава с откосами, масса грунта, консервативные операции выемки/отвала и осыпания, тесты. Запустить короткую headless-миссию.

**Этап B — автономная машина:** дрон с батареей и конечным автоматом, солнечная база, дневной цикл, планировщик, рейсы, конечное условие миссии и автоматическое редкое перемещение базы. Проверить полный цикл без GUI.

**Этап C — интерактивная визуализация:** Qt-карта, изменяющийся рельеф, профиль, параметры, управление временем, телеметрия, журнал.

**Этап D — пыль и доводка:** упрощённое пылевое поле/ветер, визуальный эффект, оптимизация узких мест, обработка ошибок, документация.

**СТОП после этапа D.** Не начинать воду/эрозию, погоду, вторую машину, детальную механику ковша, ROS, нейросети, 3D-движок, Kubernetes и т. п. без отдельного задания. Не строить ненужную универсальную платформу. Разумные инженерные упрощения важнее гиперреализма.

- Три пресета канавы: «Демо», «Средний», «Большой»; возможность Reset без перезапуска приложения.
- В конце реализации краткий отчёт: что сделано, что проверено, какие ограничения остались, что именно нужно сделать следующим шагом для будущего добавления воды и эрозии.

**Критерий успеха:** я запускаю приложение, вижу исходный участок и цель, нажимаю Start — один реальный для симуляции робот выкапывает канаву, перевозит *конечный* объём песка, расходует *конечную* энергию, возвращается на базу, заряжается от солнца; склон осыпается; пыль визуализируется; после многих рейсов миссия завершается, а баланс массы остаётся корректным.
