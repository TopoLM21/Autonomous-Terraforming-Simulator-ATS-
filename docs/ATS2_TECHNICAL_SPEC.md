## 1. Цели и режимы работы

**Основной сценарий:** солнечная мобильная база в пустыне обслуживает четыре тяжёлых электрических грузовых дрона и один облегчённый автономный экскаватор «Крот-160». Экскаватор локально вынимает грунт, заполняет жёстко-усиленные многоразовые контейнеры, дроны отвозят их на отвал, возвращают пустые, доставляют сменные аккумуляторы. В редких случаях группа дронов совместно перемещает сам экскаватор (как правило, без силовых батарей). База редко перемещается вслед за фронтом работ.

**Второй, обязательный режим:** дроны могут **самостоятельно копать старым подвесным грейфером**, вообще без экскаватора. Существующий режим работы должен сохраниться; при наличии экскаватора диспетчер вправе смешивать режимы.

**Третий, обязательный режим:** «гибридная команда» — экскаватор загружает контейнеры, часть дронов доставляет батареи/контейнеры, часть по условиям может копать самостоятельно. Никаких двух заданий одновременно одному дрону.

**Лазер:** сохранить текущий пользовательский/экспериментальный профиль **без изменения его значений**; добавить отдельный **`realistic_reference`** с более консервативными параметрами и корректным расчётом потерь/тепла.

**Основные KPI:** завершённый объём выемки (м³), м³/сутки, кВт·ч/м³, расход энергии по потребителям, занятость и ожидания машин, число рейсов, число смен батарей, масса перемещённого песка, износ контейнеров, время выполнения миссии, блокировки и их причины.

## 2. Принципы моделирования и сохранение старых функций

- Новая логистика должна обращаться к **единому API переноса грунта**. Нельзя дублировать код выемки/насыпания для разных типов техники.
- Предпочтительно чистое ядро Python без зависимостей на Qt; UI подписывается на snapshots/events.
- Все величины внутри расчётов — SI (кг, м, с, Дж, Вт), UI может отображать кВт·ч и м³/сутки.
- Симулационное время дискретно и детерминировано при одном seed. Разрешены дискретные события с длительностями; GUI не должен влиять на физику.
- Запретить мгновенную зарядку, мгновенное перемещение объектов и бесконечные склады.
- У всех конфигураций — явные идентификаторы и версии. Действующие пресеты должны продолжать загружаться.
- Сохранять пользователю возможность запускать только один дрон/без экскаватора/без лазера/без сменных батарей.

Каждый физический экземпляр имеет уникальный `id`, тип, собственную массу, расположение, состояние, текущего держателя/владельца (`holder_id`) и параметры. **Наличие в списке инвентаря не означает наличие в любом месте карты.**

|---|---|

| `CargoDrone` | позиция, установленный батарейный набор, энергоёмкость, остаток энергии, грузоподъёмность для этой конфигурации, оснащение, задание |

**Требование:** можно открыть панель «Инвентарь» и увидеть *каждый* аккумулятор и контейнер по ID: где находится, сколько весит, сколько в нём грунта / энергии, кто его зарезервировал и на какой операции занят.

## 4. Машина «Крот-160»: предлагаемый инженерный профиль

«Крот-160» — **не копия Takeuchi TB20e**, а гипотетический лёгкий автономный экскаватор для рыхлого песка с короткой стрелой, лёгкими гусеницами и опорами. Все значения настраиваемы.

| Параметр | Стартовое значение | Комментарий |
|---|---:|---|
| Сухая масса, без съёмных силовых батарей | **160 кг** | Включает раму, ковш, приводы, гусеницы, контроллер и небольшой буфер для управления |
| Активные слоты батарей | **2** | Не путать со всем складом батарей! |
| Локальное перемещение | **0,2 м/с** | Только по проходимому рельефу и после подъёма опор |
| Максимальный допустимый уклон | **10°** | Осторожное модельное допущение, отдельно от порога опрокидывания |
| Рабочий радиус стрелы | **2,0 м** | Доступность определяется текущей позицией |
| Эффективная глубина локальной выемки | **1,2 м** | Затем требуется перенастройка позиции/слоёв |
| Ковш | **15 л** | Вмещает до ~24 кг песка при 1600 кг/м³ |
| Средний коэффициент заполнения ковша | **0,75** | Один типичный цикл ~18 кг, а не автоматически 24 кг |
| Длительность цикла ковша | **35 с** | Забор, поворот, выгрузка, возврат; модельное значение |
| Средняя мощность при копании | **2,5 кВт** | Только при реально выполняемой работе |
| Пиковая мощность | **6 кВт** | Используется для ограничений батарей/приводов; не непрерывная |
| Потребление в ожидании | **0,06 кВт** | Управление/датчики; настраивать |
| Мощность движения | **0,5 кВт** | Упрощение, с поправками на уклон/песок |
| Масса перемещаемого экскаватора | 160 кг + *реально установленные батареи* + стропы | По умолчанию перед воздушной перевозкой съёмные батареи снимаются |

Внести режимы `IDLE`, `MOVING_LOCAL`, `DEPLOYING_SUPPORTS`, `DIGGING`, `FILLING_CONTAINER`, `WAITING_EMPTY_CONTAINER`, `WAITING_TRANSPORT`, `LOW_BATTERY`, `SWAP_PREPARATION`, `SWAPPING_BATTERIES`, `WAITING_RELOCATION`, `RIGGED_FOR_LIFT`, `AIR_TRANSPORT`, `FAULT`, `BLOCKED`.

**Физика устойчивости (MVP):** доступность ковша и ограничение условного усилия копания/момента опрокидывания. Нельзя позволять роботу копать произвольную вертикальную стенку «в упор» и проезжать через откос. Гусеницы, центр масс и опоры влияют на доступность операции; детальная многозвенная динамика пока не нужна. По умолчанию робот работает только с рыхлым песком.

**Обязательно:** машина должна уметь копать, даже если грузовые дроны временно заняты, но только пока есть куда реально складывать грунт — в ожидающие контейнеры (или в ограниченный рабочий бункер, если его включили), а не в бесконечный скрытый накопитель. Для экономного MVP можно вообще обойтись без промежуточного бункера.

## 5. Сменные батареи экскаватора: конфигурация и жизненный цикл

**Стартовый модуль:** ёмкость **1,5 кВт·ч**, масса **11 кг**, предел зарядной мощности **1,5 кВт** (сценарное допущение). `battery_pack_count = 4`, а **число установленных на машине — только 2**. Таким образом, при старте у машины **3,0 кВт·ч**, а другие **3,0 кВт·ч** являются запасными и могут находиться на базе.

- Две активные батареи = 22 кг. Масса копателя в работе: **182 кг**, если другие приспособления уже включены в сухую массу.
- При расходе 2,5 кВт полный заряд даёт 1,2 часа теоретически; при доступных 80% энергии — около **0,96 часа**, без поправок на ожидание и движение.
- Все четыре батареи, *если бы они были установлены одновременно*, дали бы 6 кВт·ч. Такой профиль допускается как отдельный вариант `four_slot_experimental`, но не подменяет базовый двухслотовый.
- Для замены батарей копатель **останавливает землеройные приводы** и опирается на малый буфер питания электроники. Буфер **0,1 кВт·ч** в составе сухой массы; не разрешать копать от него.
- Обычная процедура: проверка заряженных модулей → резервирование пары → отправка батарей → прибытие к боковому сервисному отсеку → остановка копания → последовательная замена → возврат снятых модулей на базу → зарядка с ограничениями.
- Возможна доставка **одним дроном двух модулей** только при соблюдении его лимита массы/энергии и наличия механизма фиксации; в базовом сценарии считать **один модуль за рейс**.
- Не считать, что дрон умеет сам вставлять батарею без оборудования: предусмотреть у «Крота» **автоматизированный боковой док** (включён в массу машины), с фиксированным временем операции. Дрон только доставляет модуль к доку и забирает снятый; механика дока условная, но не бесплатная по времени.
- Перезарядка каждой батареи идёт **в конкретном зарядном слоте на базе**. Её мощность зависит от ограничений слота, батареи и общего энергетического бюджета.
- Состояния модуля: `STORED_READY`, `RESERVED`, `IN_TRANSIT_FULL`, `INSTALLED`, `AWAITING_PICKUP`, `IN_TRANSIT_EMPTY`, `QUEUED_FOR_CHARGE`, `CHARGING`, `FAULT`. Исключить наличие одного ID в двух местах.
- Запас по SOC 20% по умолчанию; предсказывать достижение порога заранее с учётом времени доставки, а не вызывать замену только после полного разряда.

**Важно:** полностью автономная замена батарей — концептуальное оборудование под заказ. Не представлять скорость, надёжность и массу сервоприводов как серийно проверенные параметры.

## 6. Батареи и модульная оснастка грузовых дронов

Сохранить параметры текущих дронов и существующую энергетическую модель как базовую точку. Добавить возможность **действительно физической смены батарей на наземном доке**.

- Батареи дрона имеют свои объекты/ID, массу, энергию, SOC и зарядную очередь. Если реализация сейчас хранит `battery_count` и ёмкость одним числом — предоставить переходный слой.
- Замена возможна **только на станции** с роботизированным механизмом, после посадки и фиксации аппарата. Для MVP 45–90 с на операцию как настраиваемая оценка; горячая замена в воздухе **не реализуется**.
- Варианты комплектации дрона: `one_battery`, `two_batteries`. Полезная нагрузка, собственная масса и энергопотребление пересчитываются после реальной установки/снятия модулей.
- Альтернативные подвесы: `GRABBER` (копает сам), `CONTAINER_HOOK` (возит контейнеры и батареи), `HEAVY_LIFT_RIG` (совместная транспортировка машины). У каждого — масса и время смены на базе. Если существующий код не имеет понятия подвеса — ввести без переписывания полётной модели.
- **Максимальная масса груза** включает контейнер, его песок, крепления, батарейный модуль или переносимый экскаватор в зависимости от задачи. Никогда не считать песок единственной составляющей полезной нагрузки.
- Планирование рейса учитывает маршрут с грузом, пустой обратный путь, необходимую высоту над изменяющимся рельефом, энергию на операции и обязательный резерв.

## 7. Многоразовые прочные контейнеры для песка

Использовать не «невесомые мешки», а усиленные контейнеры-кассеты с собственным каркасом/петлями и проверяемой допустимой полной массой. Для MVP это жёстко-усиленный мягкий контейнер; детальную механику ткани не моделировать.

| Параметр | Предлагаемый старт |
|---|---:|
| Количество контейнеров в системе | **8 шт.** |
| Собственная масса одного контейнера | **5 кг** |
| Вместимость по объёму | **55 л** |
| Номинально допустимая полная масса контейнера | **90 кг** |
| Дополнительная масса подвеса/захвата на рейс | **2 кг** |
| Насыпная плотность песка | **1600 кг/м³**, если так задано в существующем грунтовом модуле |
| Максимум песка для дрона с грузоподъёмностью 85 кг | **78 кг** (= 85 − 5 − 2) |
| Фактический объём 78 кг песка | **48,75 л**, помещается в 55-литровый контейнер |

Формула допустимой загрузки при данном дроне:

```text
max_sand_kg = max(0, min(
    drone_payload_limit_kg - container_empty_kg - rigging_kg,
    container_gross_limit_kg - container_empty_kg,
    container_capacity_m3 * sand_density_kg_m3
))
```

Если у дрона другая конфигурация батарей и иной предел грузоподъёмности, значение автоматически меняется. **Не допускать 85 кг песка плюс контейнер при лимите груза 85 кг.**

- У контейнера отдельные состояния: `EMPTY_AT_BASE`, `EMPTY_IN_TRANSIT`, `EMPTY_AT_EXCAVATOR`, `FILLING`, `PARTIALLY_FILLED`, `FULL_READY`, `FULL_IN_TRANSIT`, `AT_DUMP`, `EMPTY_RETURNING`, `NEEDS_REPAIR`, `LOST`.
- Физическая операция засыпки учитывает массу из рельефа, груз в ковше и песок в контейнере, а также время одного цикла копания. Переход одной массы грунта между хранилищами атомарный.
- Заполнение продолжается до предела для назначенного грузового дрона или до заданного экономического порога; избыточный песок остаётся в грунте/ковше согласно реальной вместимости, но не исчезает.
- Выгрузка в отвал переносит массу из контейнера на карту. После выгрузки контейнер пуст, но его собственная масса остаётся.
- Контейнеры должны иметь возможность повторного использования. Не вводить случайные разрывы в первом этапе; можно позже ввести счётчик циклов, абразивный износ и перевод в `NEEDS_REPAIR`.
- Если все контейнеры в рейсах или заполнены, экскаватор честно переходит в `WAITING_EMPTY_CONTAINER` (или наполняет конечный рабочий буфер, если тот присутствует).

## 8. Группа дронов и совместный перенос экскаватора

По умолчанию **4 дрона**, но число настраивается. Для воздушной перевозки экскаватора разрешить создание временной команды из 2–4 и более совместимых аппаратов, если суммарная тяга и устойчивость позволяют.

- Основной MVP — **квазистатическая модель коллективного переноса**, не новая динамика винтов: групповой груз, положение, высота, углы тросов, массы строп, полезная нагрузка на каждый дрон, поправка на ускорения, запас по тяге/энергии.
- Сценарий по умолчанию: `excavator_dry_mass=160 кг`, отдельная съёмная батарея снята; масса общей подвески **12 кг** → **172 кг** переносимого груза.
- Для четырёх равно нагруженных дронов при тросах 30° к вертикали статическая эквивалентная нагрузка на каждый: `172 / (4*cos(30°)) ≈ 49,7 кг`. Не считать это достаточным доказательством безопасности: ввести запасы на манёвр, перекос и ветер.
- Если на экскаваторе всё ещё две батареи по 11 кг, переносимая масса возрастает до 194 кг со стропами; групповой планировщик **не должен автоматически игнорировать эти 22 кг**.
- **Правило по умолчанию:** перед совместной транспортировкой снять силовые батареи. Если снять их невозможно, проверять вариант с большей массой и позволять отказ операции.
- Один дрон может выполнять только одно задание. На время подъёма все участники команды зарезервированы. Диспетчер обязан проверить заряды **всех** участников перед стартом; нельзя начинать подъём, если кому-то не хватит энергии на доставку и возвращение.
- Последовательность: остановка робота → поднятие опор → подготовка стропов → сбор команды → синхронный подъём → перелёт → посадка → освобождение стропов → установка батарей при необходимости → возобновление работ.
- Проверять коллизии с рельефом по траектории **нижней точки груза**, а не только положения дронов; запретить полёт сквозь бровку канала.
- При недостатке совместной грузоподъёмности указывать `BLOCKED_INSUFFICIENT_LIFT`, а не телепортировать технику.
- Подробная динамика строп и кооперативные PID/MPC — **отдельный будущий исследовательский этап**, не обязательный для этой версии.

## 9. Автоматический диспетчер: задачи, приоритеты, очереди

Ввести централизованный планировщик логистики поверх индивидуальных конечных автоматов. Он создаёт задания из реального состояния мира, резервирует необходимые ресурсы, выбирает исполнителей и обеспечивает возврат ресурсов.

**Типы заданий:**

- `EXCAVATE_DIRECT` — дрон сам копает своим грейфером.
- `DELIVER_EMPTY_CONTAINER` — доставка пустой кассеты к экскаватору.
- `PICKUP_FULL_CONTAINER` — доставка заполненной кассеты от экскаватора в отвал.
- `RETURN_EMPTY_CONTAINER` — возврат пустой кассеты к копателю/на базу.
- `DELIVER_EXCAVATOR_BATTERY` — доставка заряженного модуля.
- `RECOVER_EMPTY_EXCAVATOR_BATTERY` — вывоз разряженного модуля на зарядку.
- `SWAP_DRONE_BATTERY` — операция на базе; выполняет док, не летающий дрон.
- `RECONFIGURE_DRONE` — смена грейфера на крюк/стропы или обратно на базе.
- `RELOCATE_EXCAVATOR_LOCAL` — экскаватор сам проезжает короткий участок.
- `RELOCATE_EXCAVATOR_AIR` — совместная транспортировка группой дронов.
- `RELOCATE_BASE` — движение базы при соблюдении её ограничений.

**Начальная логика приоритетов** (настраиваемая):

1. Безопасность, восстановление после ошибок, резерв энергии и недопущение аварий.
2. Упреждающая доставка батарей экскаватору, если он скоро остановится; возврат разряженных батарей при необходимости освободить док.
3. Вывоз заполненных контейнеров, если площадка заполнения переполнена.
4. Доставка пустых контейнеров, если экскаватор простаивает из-за нехватки тары.
5. Непосредственные рейсы с грейфером по дополнительным доступным участкам.
6. Перемещение экскаватора после завершения локального сектора (при наличии свободной команды).
7. Переезд базы только при значительной обоснованной выгоде, не во время критичных операций.

Приоритеты должны иметь **aging** или похожий механизм против вечного голодания низкоприоритетных задач. Не отправлять четыре дрона поднимать экскаватор, если это оставит воздушный груз с недопустимым SOC. Учитывать энергетическую цену операции при выборе.

**Резервирование/атомарность:** пока `container_03` в задании дрона A, диспетчер не отдаёт его дрону B. Если дрон не вылетел, задача может безопасно отмениться и освободить ресурс. При сбое — явное восстановление, а не исчезновение груза.

**Параллельность:** экскаватор может наполнять следующий контейнер, пока дрон доставляет предыдущий. Однако один контейнер нельзя одновременно заполнять и переносить.

**Необязательное более позднее улучшение:** прогнозирование загрузки и размеров партии: сколько контейнеров готовить до смены батарей, когда переставлять базу, выгоднее ли прямое копание дроном.

## 10. Энергия солнечной базы, зарядная очередь и реальный суточный баланс

Сохранить существующую модель панели/времени суток. Добавить разделение **мощности** между всеми потребителями:

- зарядка батарей дронов на доках;
- зарядка снятых батарей экскаватора;
- собственная электроника, станция батарейной автоматики;
- движение базы;
- лазерный передатчик, если включён.

Рекомендуемая конфигурация для тестов: исходная база с **20 м² солнечных панелей** и соответствующим физическим ограничением выработки. Не увеличивать площадь скрытно, чтобы новая логистика казалась быстрой. Разрешить пользователю задавать **большое разворачиваемое поле панелей** как отдельный сценарий `solar_field_large` с собственной массой/местом/временем развёртывания. Смена батарей убирает простой конкретной машины, но **не создаёт дополнительную энергию**.

- `power_available = solar_now + allowed_battery_discharge` с лимитами инвертора/батареи.
- Заряд каждого физического модуля ограничен портом, паспортным максимумом, температурой/режимом (допускается постоянный лимит в MVP) и оставшейся ёмкостью.
- Задавать число зарядных портов на базе (например, 4 универсальных); пятый модуль ждёт слота, а не заряжается невидимо.
- Если нужна одновременная работа всех дронов и экскаватора, станция может оказаться **энергетическим бутылочным горлышком**: отображать очередь зарядки и причины ограничений.
- Солнечная выработка, потери зарядки, полезная работа лазера, его тепло, энергия дронов и робота — разные статьи энергобаланса.
- В базовом профиле *никакого бесплатного генератора* и бесконечного аккумулятора. Допускается специальный профиль `infinite_energy_debug`, явно помеченный «только для экспериментов».

Не преобразовывать молча этот профиль в новый.

### 11.2. Физика и распределение мощности

Примерная формула для доставленной мощности:

```text
P_laser_optical = P_laser_electric_input * eta_electro_optical
P_reaching_rx = P_laser_optical * f_geometry * f_atmosphere * f_visibility
P_rx_optical = min(P_reaching_rx, receiver_optical_cap)
P_drone_electric = min(P_rx_optical * eta_receiver, receiver_electric_cap)
P_rx_heat = P_rx_optical - P_drone_electric
```

- Все коэффициенты в `[0, 1]` и не приводят к `P_drone_electric > P_laser_input`.
- `f_geometry` рассчитывается из площади/ориентации приёмника и пятна луча (для MVP приближённо, без волновой оптики); учесть реальные координаты передатчика и дрона.
- `f_atmosphere` зависит от длины пути и **условного** коэффициента затухания; пыль локального облака из существующей модели — отдельное множительное влияние, а не случайный глобальный процент.
- `f_visibility = 0`, если между передатчиком и приёмником земля, бровка канала, техника или запрещённая зона. При потере наведения и нарушении условий безопасности луч отключается.
- Если «лазер навёлся, но свет не принят», нельзя зачислять энергию на дрон. Расход и потери источника учитываются исходя из фактического режима передатчика; желательно регулирование, чтобы не излучать заведомо непринимаемую мощность.
- Добавить простую границу по теплу приёмника: при превышении непрерывного лимита понижать принимаемую мощность (`thermal_throttling`) или отключать лазер; для MVP модель температуры 1-го порядка достаточно.
- Массу установленного приёмника прибавлять к массе дрона и, следовательно, к мощности висения и ограничению полезной нагрузки.
- Несколько модулей передатчика / несколько приёмников — **не обязательная часть MVP**. Но использовать структуру, допускающую список лазерных устройств, и не кодировать предположение «в мире всегда один лазер».
- **Не моделировать** лазерное питание в качестве магической энергии, не допускающей расхождение луча, перекрытие и тепловые потери.

### 11.3. Сценарии сравнения

Обязательные сценарии: `laser_off`, `existing_legacy`, `realistic_reference`. Для одних и тех же геометрии/погоды/парка измерять электричество, поступившее дрону, потраченную энергию базы, массу аппарата, время зависания, м³/сутки. Лазер может питать только установленные совместимые приёмники; базовый экскаватор по лазеру не питается.

## 12. Выбор рабочих участков, трасса и высотная отметка

Не менять текущую цель выемки/обработку рельефа. Для длинного канала в будущем нужен модуль реальных DEM, но сейчас новые логистические сущности работают на имеющейся heightfield-сетке.

- Сохранять возможность задавать проектную **абсолютную высоту дна** (относительно общего вертикального датума), а не только фиксированную глубину относительно поверхности. Там, где рельеф выше, выемка глубже.
- Экскаватор может вынимать только достижимые клетки: текущая точка стоянки, радиус стрелы, достижимая высота/глубина, устойчивая площадка.
- При исчерпании локального фронта работ планировщик выбирает короткий проходимый переезд или совместный воздушный перенос на новую площадку.
- При слишком глубокой/крутой выемке симулятор должен сообщать о невозможности доступа, а не рисовать экскаватор в воздухе.
- Учитывать путь груза **из глубокой выемки на поверхность** при расчёте энергии и доступности дронов.
- Будущая трасса Каттара / Средиземное море / озёра Тошка — отдельный географический модуль; **в этой реализации не подключать внешние DEM без необходимости**. Главное — корректное API для карты высот и целевого профиля.

## 13. Панель управления и инвентарь в GUI

Не заменять текущий GUI целиком, а добавить вкладки/док-панели с понятными состояниями и действиями. Если приложение уже на PySide6 — использовать его, не внедрять другую библиотеку без причины.

**Минимальные панели:**

1. **Карта:** дроны с номерами, экскаватор, солнечная база, рабочие и складские площадки, наполненные/пустые контейнеры, зоны доступности стрелы, маршруты рейсов, изменяющийся рельеф.
2. **Флот:** таблица дронов с задачей, типом оснастки, текущим грузом (масса предмета + масса песка), зарядом, расчётным запасом хода, статусом лазера.
3. **Экскаватор:** режим, позиция, установленная пара батарей (ID), локальная производительность, ковш, активный контейнер, причины ожидания, запрос на переезд.
4. **Склад:** поштучно контейнеры, батареи дронов, батареи экскаватора, стропы, грейферы и прочие сменные подвесы. Фильтр по месту/состоянию/заряду.
5. **Энергетика:** солнечная генерация, SOC базы, потребление по видам, очередь зарядки, свободные зарядные слоты, лазерная мощность и потери.
6. **Диспетчер:** очередь заданий (приоритет, ресурсы, исполнитель, ETA как внутренняя модель), причины блокировки и журнал событий.
7. **Эксперименты:** выбор профиля лазера, конфигурации батарей, числа дронов/контейнеров, включение экскаватора и режима прямой выемки дроном.

**Управление:** Play/Pause/Reset, ×1/×10/×50/×200 (как поддерживает старый движок), сохранение/загрузка конфигурации, запуск batch-сценариев в headless-режиме. Пользователь должен увидеть, почему экскаватор стоит: нет контейнера, нет заряженной пары батарей, участок недоступен, экскаватор ждёт переезда и т. п.

## 14. Физическая корректность, инварианты, тупики и тесты

### 14.1. Инварианты

**Масса грунта.** Сумма массы песка на карте, в ковше, во всех контейнерах, грейферах и в конечном рабочем бункере остаётся постоянной (если явно не задан внешний импорт/экспорт). Массу контейнера **не смешивать** с песком.

**Инвентарь.** Количество предметов каждого типа сохраняется. Один `BatteryModule` или `SoilContainer` в конкретный момент находится ровно в одном месте. Одну батарею нельзя одновременно зарядить и перевозить. Контейнер не может одновременно находиться в двух дронах.

**Энергия.** Не допускать отрицательных SOC или зарядки выше 100%; не создавать энергию при смене модуля. Любая подпитка от лазера уменьшает доступную энергию наземной базы с учётом её КПД.

**Нагрузка.** Масса полезного груза включает предмет + содержимое + крепления; масса самого дрона включает установленные батареи и приёмник. Смена конфигурации влияет на грузоподъёмность и полётную мощность.

**Недоступность.** Нельзя копать вне рабочего радиуса экскаватора, ездить по недопустимому склону, переносить груз без нужной команды или лететь через стенку канала.

### 14.2. Обязательные автотесты

1. **`test_legacy_regression`**: старый сценарий «один дрон с грейфером» работает без созданного экскаватора; существующая физика/лазерный профиль не исчезли.
2. **`test_battery_slots_not_inventory`**: четыре модуля по 1,5 кВт·ч существуют, но два установленных дают машине ровно 3 кВт·ч.
3. **`test_battery_swap_atomic`**: модуль извлечён, доставлен, вставлен, старый вернулся; дубликатов нет; машина не копает на одном управляющем буфере.
4. **`test_charging_energy_conservation`**: при нулевой генерации и пустом аккумуляторе базы заряд батарей не растёт; зарядка ограничена портами и КПД.
5. **`test_container_payload_with_tare`**: груз при 85 кг пределе, 5 кг контейнере, 2 кг креплениях не превышает 78 кг песка; при уменьшенной грузоподъёмности лимит падает.
6. **`test_container_cycle_mass`**: выемка → контейнер → дрон → отвал → возврат пустого; грунт не появляется/не исчезает.
7. **`test_excavator_waits_for_empty_container`**: при всех занятых контейнерах копатель не продолжает добычу в несуществующий склад.
8. **`test_direct_drone_digging`**: самостоятельная экскавация дроном по-прежнему доступна при выключенном копателе, а также в смешанном сценарии.
9. **`test_collective_lift`**: группа проверяет массу корпуса + стропы, учитывает установленные батареи, запрещает рейс при нехватке запаса тяги/SOC.
10. **`test_laser_reference_power`**: при входных 5 кВт и предположенных КПД получается ~0,6 кВт на приёмнике и ~0,9 кВт тепла; входная энергия списывается с базы.
11. **`test_laser_blocked_or_overheated`**: после перекрытия луча энергия перестаёт поступать; тепловой лимит реально ограничивает мощность.
12. **`test_inventory_reservation`**: два дрона не могут получить одно и то же физическое задание или контейнер.
13. **`test_deadlock_recovery`**: отсутствие батарей/контейнеров/проходимой площадки приводит к понятному `WAITING`/`BLOCKED`, а не бесконечному циклу без событий.
14. **`test_deterministic_headless`**: повторный прогон с тем же seed/конфигурацией даёт те же результаты.
15. **`test_completed_small_scenario`**: маленький участок может быть полностью выработан новой системой с контейнерами и хотя бы одним реальным циклом замены батареи; тест завершается за ограниченное число шагов.

## 15. Этапы реализации: не пытаться написать всё сразу

### Этап A — инвентарь и нагрузка (обязательный первый)
- Сущности `BatteryModule`, `SoilContainer`, `Rigging`, точки хранения, резервирование объектов.
- Конечная масса груза для дрона; поддержка старого режима без инвентаря через миграцию/адаптер.
- Headless-тесты сохранения инвентаря и грунта.
- **Промежуточный результат:** один дрон действительно переносит контейнер известной массы, выгружает песок на рельеф, возвращает пустой.

### Этап B — «Крот-160» и накопление очереди (обязательный)
- Локальная ходовая, область ковша, слабая стабилизация, цикл копания, наполнение конкретного контейнера.
- Экскаватор ждёт контейнер, дроны вывозят и возвращают, возможно параллельная работа.
- **Промежуточный результат:** робот + 1–2 дрона выполняют короткую миссию без лазера и без смены батарей.

### Этап C — модульные батареи и диспетчер (обязательный)
- 2 активных слота копателя, 4 модуля в общем инвентаре, физическая доставка/снятие/зарядка; дроновые батареи меняются на наземном доке.
- Очереди, резервы, приоритеты, no-duplication/no-deadlock; ограничение зарядных слотов.
- **Промежуточный результат:** миссия проходит минимум одну штатную смену батареи, не вынимая копатель из канавы.

### Этап D — флот, смешанные задания и совместный подъём (обязательный)
- Поддержка четырёх дронов, грейфер как альтернативная оснастка, планировщик нескольких задач.
- Квазистатический совместный перенос копателя без батарей; отдельная доставка батарей.
- **Промежуточный результат:** дроны могут перенести робота, затем обслуживать поток грунта; один из дронов при подходящих условиях может копать самостоятельно.

### Этап E — лазер и UI (обязательный)
- Текущий лазер без регрессии; новый `realistic_reference`, затухание, отключение при перекрытии, масса/тепло приёмника.
- GUI: инвентарь поштучно, диспетчер, состояния батарей, очереди контейнеров, энергетика, выбор конфигураций.
- **Промежуточный результат:** переключение лазерных профилей и сравнимые прогоны в GUI/headless.

### Этап F — стабилизация и измерения (обязательный)
- Автотесты раздела 14, профилирование, воспроизводимость, пакетный прогон сценариев S0–S9.
- Документация, ограничения, известные расхождения с настоящими машинами.
- После этого **остановиться**: не добавлять воду, гидрологию Каттары и полноценную трёхмерную аэродинамику без нового запроса.

## 18. Финальная приёмка и формат отчёта Codex

Codex сдаёт:

1. Изменённый рабочий проект, **без потери исходных сценариев**.
2. Обновлённый README и описание параметров, включая различия между подтверждёнными характеристиками реальной техники и модельными допущениями.
3. Headless-демо с одним копателем, четырьмя дронами, восемью контейнерами и четырьмя батарейными модулями копателя; демонстрируется выемка → заполнение → вывоз → выгрузка → возврат контейнера, а также минимум одна смена батарей.
4. Работающую UI-панель инвентаря и телеметрии; в GUI видны причины простоя.
5. Автоматические тесты, запуск которых Codex выполняет самостоятельно; результаты проверок.
6. Сравнительную таблицу для S0–S9 (допустимо сокращение до S0, S2, S3, S4, S5, S6 при ограничениях среды), в одинаковых единицах.
7. Перечень функций, оставленных для будущей версии: реальная DEM-трасса к Каттаре, вода/эрозия, детальная динамика группового полёта, износ/отказ техники, многомодульная лазерная установка.

**Критерий успеха:** на карте есть копатель и 4 дрона; робот достаёт конечную массу песка и загружает конкретные контейнеры, дроны их перевозят и возвращают пустыми, батареи движутся по реальной цепочке «база → робот → база → зарядка», а при перемещении робота дроны поднимают именно его сухой корпус с учётом строп. Система честно учитывает массу и энергию, не зависает в недостижимом состоянии, а существующий одиночный режим продолжает работать.

## Справочные источники для инженерных ориентиров

- **PowerLight Technologies ARC:** <https://powerlighttech.com/wireless-power/> — подтверждены ориентиры 800 Вт peak / ~600 Вт avg, масса приёмника 2,8 кг. Прочие значения профиля `realistic_reference` в этом ТЗ не являются подтверждёнными спецификациями изделия.
- **Takeuchi TB20e:** <https://www.takeuchi-us.com/equipment/electric-machines/tb20e> — серийный электрический мини-экскаватор ~1930 кг; не используется в качестве массогабаритного шаблона «Крота».
- **NASA RASSOR 2.0:** <https://ntrs.nasa.gov/citations/20210011366> — подтверждён пример экспериментального облегчённого робота для рыхлого реголита (~66 кг); **не доказывает** характеристики задуманного экскаватора 160 кг с обычным ковшом на Земле.

**Примечание о масштабе:** цель этого релиза — корректная логистика и сопоставимые инженерные эксперименты. Реальная роботизированная техника потребовала бы отдельного проектирования прочности, запылённости, управления, безопасности лазера и обслуживания. Не выдавать симулятор за сертифицированный проект строительной системы.
